# Cardiac arrest simulation integration

The feature lives in `backend/app/cardiac_arrest` and the Cardiac Arrest React workspace. Existing public optimization schemas and the general scenario simulator remain compatible.

- Reports are stored as SQLite JSON documents in `backend/.simulation/cardiac.sqlite3` (override with `CARDIAC_DB_PATH`). A SQLite `BEGIN IMMEDIATE` transaction covers allocation and reservation, including across backend workers. Restarting the server preserves incidents and commitments.
- Dispatch adapts each report to the existing `IncidentInput` with type `CARDIAC_ARREST`, all reported victims represented as critical simulation demand. It calls `solve_emergency_dispatch_optimization`; no substitute ambulance solver is introduced. The expanded cardiac sandbox generates one 24/7 public mock AED and a mock post with one ALS plus one BLS vehicle at each of the 339 hospital coordinates. The original 8 AED records and 12 scenario vehicles remain, yielding 347 AED records and 690 vehicles. IDs are deterministic and unique.
- `resource_catalog.py` derives resources directly from the hospital directory without editing it. All 349 bases and 339 hospital candidates are available to the cardiac MILP statewide; discovery defaults to 25 km but does not restrict the statewide fleet. The cardiac-only receiving profile assumes six places and the required ED/ICU/equipment/specialist support at every site. These are explicitly synthetic capabilities, not verified cardiac-centre credentials. Original simulator capabilities and fleet data remain separate and unchanged.
- `GET /api/cardiac-arrest/catalog` exposes all AEDs and individual fleet slots with active reservations and summary totals. The cardiac map shows clustered AED and ambulance-post layers, with statewide and incident views. Cluster numbers count locations; each generated hospital post represents two vehicles. Available nearby resources and assigned units are shown separately.
- Active cardiac incidents reserve individual synthetic fleet slots, hospital intake capacity, AEDs and responders. The existing stateless `/api/optimize` endpoint does not reserve resources; its independent experiments do not share this registry. Cancel or complete a cardiac incident to release its commitments.
- AED and responder records are entirely synthetic, including the generated hospital AED inventory. AED access windows use Asia/Kolkata at the report's simulation timestamp. Restricted, closed, non-operational, unavailable and unknown-status devices are excluded. Responder eligibility requires verified simulated CPR or CPR_AED training and availability.
- Resource selection and solver inputs use the existing 1.35× Haversine road-distance estimator. Walking is assumed at 5 km/h. The map reuses the existing routing service for ambulance route geometry, labels OSRM/fallback results, and keeps simulation ETAs tied to the controlled estimator. A hospital-origin ambulance may load the AED from its own site during its 15-second mobilization and deliver it at ambulance arrival. Otherwise AED collection uses a walking responder/runner estimate. If its ambulance is replaced before arrival, an undelivered AED assignment is replanned too.
- All timeline offsets are simulated seconds since report time, independent of wall-clock API latency. Resource states and incident states are separate. CPR/AED-use times only exist after explicit simulation actions. No shock or survival outcome is inferred.
- Fixed timing assumptions: 2 seconds to assign resources, 10 seconds from assignment to responder acceptance, 15 seconds to departure, 4 minutes on scene (API configurable), and 1 minute for handover. Actual solver computation is reported separately in milliseconds. Hospital projections show the last allocated arrival; the observed dashboard metric is the first recorded hospital arrival.
- A/B/C comparison is a projection from the same availability snapshot, coordinates and fixed assumptions (no randomness, sample size one). It does not reserve additional resources. Modes B/C use the earliest modelled ambulance delivery when available; otherwise B uses a fictional retrieval runner and C a CPR_AED collector, plus a direct responder when available. Existing saved runs retain their original snapshots; new reports use the expanded inventory.
- Deterministic text extraction always runs. Optional Gemini extraction can be enabled with `GEMINI_API_KEY` and `GEMINI_MODEL`; results must validate and never overwrite caller-entered known fields. No AI output gates dispatch. Without configuration, the feature needs no AI service.
- The optional adapter uses Google's [Generate Content JSON output API](https://ai.google.dev/gemini-api/docs/structured-output) with server-side schema validation, bounded timeouts and no automatic retries. Configure a currently supported model ID explicitly; the default path makes no AI network request.
- Disruptions replan affected future assignments. Road closures add an explicit 50% remaining-travel delay. Unavailable vehicles and full hospitals trigger the same existing solver again before transport; journeys already transporting are preserved. Notifications and all resource actions are simulated only.
