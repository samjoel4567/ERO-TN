# Cardiac arrest simulation integration

The feature lives in `backend/app/cardiac_arrest` and the Cardiac Arrest React workspace. Existing public optimization schemas and the general scenario simulator remain compatible.

- Reports are stored as SQLite JSON documents in `backend/.simulation/cardiac.sqlite3` (override with `CARDIAC_DB_PATH`). A SQLite `BEGIN IMMEDIATE` transaction covers allocation and reservation, including across backend workers. Restarting the server preserves incidents and commitments.
- Dispatch adapts each report to the existing `IncidentInput` with type `CARDIAC_ARREST`, all reported victims represented as critical simulation demand. It calls `solve_emergency_dispatch_optimization`; no substitute ambulance solver is introduced. Bases and hospital profiles come from `services/data_loader.py`. ED, ICU and emergency-equipment flags must be explicitly true; these are scenario capabilities, not verified cardiac-centre credentials. Existing critical-patient eligibility rules still apply.
- Active cardiac incidents reserve individual synthetic fleet slots, hospital intake capacity, AEDs and responders. The existing stateless `/api/optimize` endpoint does not reserve resources; its independent experiments do not share this registry. Cancel or complete a cardiac incident to release its commitments.
- New AED and responder JSON records are entirely synthetic. AED access windows use Asia/Kolkata at the report's simulation timestamp. Restricted, closed, non-operational, unavailable and unknown-status devices are excluded. Responder eligibility requires verified simulated CPR or CPR_AED training and availability.
- Resource selection and solver inputs use the existing 1.35× Haversine road-distance estimator. Walking is assumed at 5 km/h. The map reuses the existing routing service for ambulance route geometry, labels OSRM/fallback results, and keeps simulation ETAs tied to the controlled estimator. AED trips use walking estimates, never driving routes.
- All timeline offsets are simulated seconds since report time, independent of wall-clock API latency. Resource states and incident states are separate. CPR/AED-use times only exist after explicit simulation actions. No shock or survival outcome is inferred.
- Fixed timing assumptions: 2 seconds to assign resources, 10 seconds from assignment to responder acceptance, 15 seconds to departure, 4 minutes on scene (API configurable), and 1 minute for handover. Actual solver computation is reported separately in milliseconds. Hospital projections show the last allocated arrival; the observed dashboard metric is the first recorded hospital arrival.
- A/B/C comparison is a projection from the same availability snapshot, coordinates and fixed assumptions (no randomness, sample size one). It does not reserve additional resources. AED mode explicitly models a fictional retrieval runner; full mode uses a CPR_AED responder for collection, with a second responder for direct attendance when available.
- Deterministic text extraction always runs. Optional Gemini extraction can be enabled with `GEMINI_API_KEY` and `GEMINI_MODEL`; results must validate and never overwrite caller-entered known fields. No AI output gates dispatch. Without configuration, the feature needs no AI service.
- The optional adapter uses Google's [Generate Content JSON output API](https://ai.google.dev/gemini-api/docs/structured-output) with server-side schema validation, bounded timeouts and no automatic retries. Configure a currently supported model ID explicitly; the default path makes no AI network request.
- Disruptions replan affected future assignments. Road closures add an explicit 50% remaining-travel delay. Unavailable vehicles and full hospitals trigger the same existing solver again before transport; journeys already transporting are preserved. Notifications and all resource actions are simulated only.
